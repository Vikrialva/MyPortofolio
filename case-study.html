The brief

Novu is a B2B notification infrastructure platform — it lets developers route, manage, and monitor notifications across email, SMS, push, and in-app channels. The backend was a two-year-old PHP monolith with no clear module boundaries, the dashboard was server-rendered jQuery, and every new feature took longer to ship than the last. By early 2025, deploys were weekly at best, page loads regularly exceeded four seconds, and churn in the 14-day trial window was climbing.

My mandate was simple: rebuild the platform end to end without freezing feature work. The budget was fixed and we had six weeks to cut over.

"We're losing users in the first 20 minutes. They sign up, see the dashboard, and just bounce. The product does exactly what they need — they just can't get to it fast enough."

Discovery & technical audit

Audit of the existing system

I spent the first week mapping the existing architecture and instrumenting everything. The findings were brutal but predictable:

  • The dashboard made 47 API calls on first load — many duplicated or sequential when they could be parallel
  • No database indexes on the three hottest query paths; the notification log query did a full table scan across 40M rows
  • Business logic leaked into controllers and templates alike — zero test coverage anywhere
  • Trial users specifically wanted a "get your first notification live" path, not a feature overview

Profiling

I profiled the slowest user journeys with distributed tracing and found that 80% of dashboard latency came from N+1 queries and unpaginated list endpoints. This told me exactly where the rewrite would pay for itself fastest.

Existing architecture with latency hot spots annotated during the audit phase.

Technical strategy

Based on the audit, I built the rebuild plan around three principles:

Strangler, not big bang

New Laravel services sat behind a proxy alongside the legacy monolith. Routes migrated one by one — no risky cutover weekend.

Schema-first

A clean MySQL schema with proper indexes and constraints designed before any API code. Migrations versioned and reversible.

Tested from day one

PHPUnit unit + Playwright e2e tests in CI for every merged PR. Coverage gates on the new codebase: minimum 85% before anything ships.

Process

Week 1 · Schema & data migration

I modelled the new MySQL schema around access patterns rather than entities: composite indexes for every dashboard query, JSON columns only where truly schemaless data was needed, and partitioning on the notification log table by month. A dual-write phase kept legacy and new databases in sync while queued backfill jobs migrated 40M rows with zero downtime.

Key technical decisions

Partitioning the notification log

The log table grew by ~2M rows a week and was the single biggest latency source. I partitioned it monthly in MySQL and added covering indexes for the three dashboard query shapes. Combined with keyset pagination replacing OFFSET queries, p95 response time dropped from 2.4s to under 200ms — without touching application code.

Real-time logs over WebSocket

Previously the dashboard polled the notification log every 10 seconds — 6 requests per minute per open tab. I replaced this with a Redis pub/sub layer feeding Laravel Echo over WebSockets. Users now see events within 100ms of them firing, and backend load from dashboard traffic dropped 90%.

SSR first paint + React Query

Static panels (stats, channel health) are server-rendered by Laravel with the initial HTML; interactive panels hydrate on demand through a cached React Query layer with optimistic mutations. First load went from 47 API calls to 6, and LCP from 4.1s to 1.3s on mid-range hardware.

Results

The rebuild shipped in week 6, exactly on schedule. Metrics were tracked over the following 6 weeks post-launch compared to the same prior period.

  • Page load time (p95): 4.1s → 1.6s (−60%)
  • Average API response time: −70%
  • Trial-to-paid conversion rate: +27%
  • Onboarding completion (first notification live): 21% → 68%
  • Deploys per week: 1 → 12 (CI/CD pipeline)
  • Uptime since launch: 99.98%

Reflections

The biggest lesson from this project: most "slow product" complaints are really architecture complaints. The frontend was blamed for years, but 80% of the latency lived in N+1 queries and missing indexes. Measuring before rewriting meant we fixed the right things first.

If I were to do it again, I'd push harder for a longer discovery phase. Six weeks is tight for a full-stack rebuild, and we made two schema decisions based on incomplete access-pattern data that needed revision in month two. The strangler approach absorbed both changes safely — but another week of profiling up front would have caught them earlier.
